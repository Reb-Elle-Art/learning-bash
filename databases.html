database 101

databases.

Categories, concepts, and eventually -- queries

Databases come in several fundamentally different shapes. The right one depends on what your data looks like and how you need to use it. Click to expand.

Relational
SQL databases
Data stored in tables with rows and columns. Relationships between tables defined by keys.
e.g. PostgreSQL, MySQL, SQLite
v
How it works
Think of it like a very powerful spreadsheet. Data lives in tables -- each row is a record, each column is a field. Tables can reference each other through shared keys. You query data using SQL (Structured Query Language).
Good for
Structured data with clear relationships. Financial records, user accounts, orders, inventories -- anything where consistency and relationships matter.
Example mental model
Users table: id | name | email Orders table: id | user_id | product | price ^--- references Users.id
Key idea
The schema (structure) is defined upfront. Every row in a table must follow the same shape. This rigidity is a feature -- it enforces consistency.
Document
NoSQL -- document stores
Data stored as flexible documents (usually JSON-like). No fixed schema required.
e.g. MongoDB, CouchDB, Firestore
v
How it works
Instead of rows in tables, you store documents -- self-contained blobs of data, usually in JSON format. Each document can have a different structure. No need to define a schema first.
Good for
Flexible or evolving data structures. Content management, user profiles, product catalogs where each item might have different fields.
Example mental model
{ "name": "Anazial", "email": "hi@example.com", "preferences": { "theme": "dark" } }
Key idea
Schema-flexible. Documents in the same collection don't have to look the same. Great for rapid development when your data shape is still evolving.
Key-Value
NoSQL -- key-value stores
The simplest database model. Every piece of data is stored and retrieved by a unique key.
e.g. Redis, DynamoDB, Memcached
v
How it works
Like a giant dictionary or lookup table. You store a value under a key, and retrieve it by that key. Extremely fast -- often held entirely in memory.
Good for
Caching, session storage, leaderboards, real-time features. Anywhere you need to look something up by a known identifier very quickly.
Example mental model
SET session:abc123 "user_id=42" GET session:abc123 --> "user_id=42"
Key idea
Sacrifices complexity for speed. You can't easily query "all values where X" -- you retrieve by key only. Often used alongside a relational database, not instead of one.
Graph
NoSQL -- graph databases
Data stored as nodes and edges. Built for highly connected data and relationship traversal.
e.g. Neo4j, Amazon Neptune
v
How it works
Data is represented as a network of nodes (things) connected by edges (relationships). Querying means traversing those connections.
Good for
Social networks, recommendation engines, fraud detection, knowledge graphs -- anything where the connections between things are as important as the things themselves.
Example mental model
(Anazial) --[FOLLOWS]--> (Enid) (Enid) --[RUNS]--> (nginx) (Anazial) --[USES]--> (bash)
Key idea
Relational databases can model relationships too, but graph databases make traversing deep, complex relationships much faster and more natural.
Time-series
Optimized for time-stamped data
Built specifically for data that arrives in time order and is queried by time ranges.
e.g. InfluxDB, TimescaleDB, Prometheus
v
How it works
Every data point is associated with a timestamp. The database is optimized for writing large volumes of time-ordered data and querying ranges or aggregates over time.
Good for
Server metrics, IoT sensor data, financial tick data, logs, monitoring dashboards. Anywhere you're asking "what happened between X time and Y time".
Example mental model
2026-05-23 22:05:01 cpu_usage=12% 2026-05-23 22:05:02 cpu_usage=14% 2026-05-23 22:05:03 cpu_usage=11%
Columnar
Column-oriented stores
Like relational but stores data by column rather than by row. Built for analytics at scale.
e.g. BigQuery, Redshift, Cassandra
v
How it works
Traditional databases store each row together on disk. Columnar databases store each column together. This makes scanning a single column across millions of rows extremely fast.
Good for
Data warehousing, analytics, business intelligence. Queries like "average revenue across all orders last year" are much faster than in row-oriented databases.
Key idea
Optimized for reads across many rows, not for frequent writes or updates to individual rows. You'd use this alongside a transactional database, not instead of it.

The vocabulary of databases. Click to expand.

Schema
The structure definition of a database
v
A schema defines the shape of your data -- what tables exist, what columns they have, what types of data each column accepts. In relational databases the schema is strict and defined upfront. In document databases it can be loose or absent entirely.
SQL
Structured Query Language
v
The language used to interact with relational databases. You use it to create tables, insert data, and query for results. SQL is a standard -- the same core syntax works across PostgreSQL, MySQL, SQLite and others, with small differences.
SELECT name FROM users WHERE id = 42;
NoSQL
Not Only SQL
v
A broad term for databases that don't use the traditional relational table model. Includes document, key-value, graph, and time-series databases. Not a single thing -- just means "not a traditional SQL database". Each type has its own query language or API.
Primary key
A unique identifier for each row
v
Every row in a relational database table needs a unique identifier -- the primary key. Usually an auto-incrementing integer (1, 2, 3...) or a UUID. It's how you refer to a specific record unambiguously.
id | name | email 1 | Anazial | ... 2 | Enid | ... ^-- primary key
Foreign key
A reference to another table's primary key
v
How relational databases link tables together. A foreign key in one table points to the primary key in another. This is what makes relational databases relational -- you can connect data across tables without duplicating it.
orders table: order_id | user_id | product 1 | 42 | keyboard ^-- foreign key pointing to users.id
Index
A lookup structure for faster queries
v
Without an index, finding a row means scanning the whole table. An index is a separate data structure that lets the database jump directly to matching rows. Think of it like the index at the back of a book. Speeds up reads but slows down writes slightly.
CRUD
The four basic database operations
v
Every database interaction is one of four things: Create, Read, Update, Delete. In SQL these map to INSERT, SELECT, UPDATE, DELETE. You'll see CRUD used everywhere in software development as a shorthand for basic data operations.
Create --> INSERT Read --> SELECT Update --> UPDATE Delete --> DELETE
Transaction
A group of operations that succeed or fail together
v
A transaction bundles multiple operations so they either all succeed or all fail -- never half-complete. The classic example: transferring money means subtracting from one account and adding to another. If the system crashes in between, you don't want one to happen without the other.
ACID
Properties of reliable transactions
v
ACID stands for Atomicity (all or nothing), Consistency (data stays valid), Isolation (transactions don't interfere), Durability (committed data persists). Relational databases are ACID-compliant. Many NoSQL databases trade some ACID properties for speed or scale.
ORM
Object Relational Mapper
v
A library that lets you interact with a database using your programming language instead of raw SQL. Instead of writing SELECT * FROM users, you might write User.find(42). Easier to work with but adds a layer of abstraction. Examples: SQLAlchemy (Python), ActiveRecord (Ruby), Prisma (JavaScript).
