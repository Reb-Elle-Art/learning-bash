Databases come in several fundamentally different shapes. The right one depends on what your data looks like and how you need to use it. Click to expand.

Database types
R Relational / SQL PostgreSQL, MySQL, SQLite ▾
Tables, rows, columns -- like a very powerful spreadsheet
How it works
Data lives in tables -- each row is a record, each column is a field. Tables can reference each other through shared keys. You query data using SQL (Structured Query Language).
Good for
Structured data with clear relationships. Financial records, user accounts, orders, inventories -- anything where consistency and relationships matter.
Example
Users table: id | name | email Orders table: id | user_id | product | price ^--- references Users.id
Key idea
The schema (structure) is defined upfront. Every row must follow the same shape. This rigidity is a feature -- it enforces consistency.
D Document store MongoDB, CouchDB, Firestore ▾
JSON-like documents -- flexible, no fixed schema required
How it works
Instead of rows in tables, you store documents -- self-contained blobs of data, usually in JSON format. Each document can have a different structure.
Good for
Flexible or evolving data structures. Content management, user profiles, product catalogs where each item might have different fields.
Example
{ "name": "Anazial", "email": "hi@example.com", "preferences": { "theme": "dark" } }
Key idea
Schema-flexible. Documents in the same collection don't have to look the same. Great for rapid development when your data shape is still evolving.
K Key-value store Redis, DynamoDB, Memcached ▾
The simplest model -- store and retrieve by a unique key
How it works
Like a giant dictionary. You store a value under a key, and retrieve it by that key. Extremely fast -- often held entirely in memory.
Good for
Caching, session storage, leaderboards, real-time features. Anywhere you need to look something up very quickly by a known identifier.
Example
SET session:abc123 "user_id=42" GET session:abc123 --> "user_id=42"
Key idea
Sacrifices complexity for speed. You can't easily query "all values where X" -- you retrieve by key only. Often used alongside a relational database, not instead of one.
G Graph database Neo4j, Amazon Neptune ▾
Nodes and edges -- built for highly connected data
How it works
Data is represented as a network of nodes (things) connected by edges (relationships). Querying means traversing those connections.
Good for
Social networks, recommendation engines, fraud detection -- anything where the connections between things are as important as the things themselves.
Example
(Anazial) --[USES]--> (bash) (Enid) --[RUNS]--> (nginx) (Anazial) --[CONNECTS_TO]--> (Enid)
Key idea
Relational databases can model relationships too, but graph databases make traversing deep, complex relationships much faster and more natural.
T Time-series InfluxDB, TimescaleDB, Prometheus ▾
Optimized for time-stamped data and range queries
How it works
Every data point is associated with a timestamp. The database is optimized for writing large volumes of time-ordered data and querying ranges or aggregates over time.
Good for
Server metrics, IoT sensor data, financial tick data, logs, monitoring dashboards. Anywhere you're asking "what happened between X time and Y time".
Example
2026-05-23 22:05:01 cpu_usage=12% 2026-05-23 22:05:02 cpu_usage=14% 2026-05-23 22:05:03 cpu_usage=11%
C Columnar store BigQuery, Redshift, Cassandra ▾
Column-oriented storage -- built for analytics at scale
How it works
Traditional databases store each row together on disk. Columnar databases store each column together. This makes scanning a single column across millions of rows extremely fast.
Good for
Data warehousing, analytics, business intelligence. Queries like "average revenue across all orders last year" are much faster than in row-oriented databases.
Key idea
Optimized for reads across many rows, not for frequent writes to individual rows. Usually used alongside a transactional database, not instead of it.

The vocabulary of databases. Click to expand.

Schema
The structure definition
▾
Defines the shape of your data -- what tables exist, what columns they have, what types each column accepts. In relational databases the schema is strict and defined upfront. In document databases it can be loose or absent entirely.
SQL
Structured Query Language
▾
The language used to interact with relational databases. Used to create tables, insert data, and query for results. SQL is a standard -- the same core syntax works across PostgreSQL, MySQL, SQLite with small differences.
SELECT name FROM users WHERE id = 42;
NoSQL
Not Only SQL
▾
A broad term for databases that don't use the traditional relational table model. Includes document, key-value, graph, and time-series databases. Not a single thing -- just means "not a traditional SQL database". Each type has its own query language or API.
Primary key
Unique identifier for each row
▾
Every row in a relational table needs a unique identifier. Usually an auto-incrementing integer (1, 2, 3...) or a UUID. It's how you refer to a specific record unambiguously.
id | name | email 1 | Anazial | ... 2 | Enid | ... ^-- primary key
Foreign key
A reference to another table
▾
How relational databases link tables together. A foreign key in one table points to the primary key in another. This is what makes relational databases relational -- connecting data across tables without duplicating it.
orders: order_id | user_id | product 1 | 42 | keyboard ^-- foreign key --> users.id
Index
A lookup structure for faster queries
▾
Without an index, finding a row means scanning the whole table. An index is a separate data structure that lets the database jump directly to matching rows. Like the index at the back of a book. Speeds up reads but slows writes slightly.
CRUD
The four basic operations
▾
Every database interaction is one of four things: Create, Read, Update, Delete. In SQL these map to INSERT, SELECT, UPDATE, DELETE. You'll see CRUD everywhere in software development as shorthand for basic data operations.
Create --> INSERT Read --> SELECT Update --> UPDATE Delete --> DELETE
Transaction
Operations that succeed or fail together
▾
A transaction bundles multiple operations so they either all succeed or all fail -- never half-complete. The classic example: transferring money means subtracting from one account and adding to another. If the system crashes in between, you don't want one to happen without the other.
ACID
Properties of reliable transactions
▾
Atomicity (all or nothing), Consistency (data stays valid), Isolation (transactions don't interfere), Durability (committed data persists). Relational databases are ACID-compliant. Many NoSQL databases trade some ACID properties for speed or scale.
ORM
Object Relational Mapper
▾
A library that lets you interact with a database using your programming language instead of raw SQL. Instead of writing SELECT * FROM users, you might write User.find(42). Examples: SQLAlchemy (Python), ActiveRecord (Ruby), Prisma (JavaScript).

Real world database choices -- and the reasoning behind them. Click to expand.

Real world applications
R Instagram PostgreSQL ▾
User accounts, posts, likes, follows
Why relational
Instagram's core data is deeply relational -- a user has posts, posts have likes, likes belong to users, users follow users. These relationships are well-defined and consistent. PostgreSQL enforces that structure and handles complex queries across those relationships efficiently.
The tradeoff
As Instagram scaled to billions of users they layered other databases on top (Cassandra for feeds, Memcached for caching) -- but PostgreSQL remains the source of truth for structured user data.
D Airbnb MongoDB (listings) ▾
Property listings with highly variable attributes
Why document
Every Airbnb listing is different. A treehouse has different attributes than a city apartment -- different amenities, different room types, different house rules. A rigid relational schema would require hundreds of nullable columns or complex joins. A document store lets each listing carry exactly the fields it needs.
The tradeoff
Bookings and payments -- which are strictly structured and transactional -- use relational databases. The document store is specifically for the flexible listing data.
K Twitter / X Redis (caching) ▾
Timeline caching, session storage, rate limiting
Why key-value
When millions of users load their timeline simultaneously, you can't query the database fresh every time -- it would collapse. Redis stores pre-computed timelines in memory keyed by user ID. A timeline request becomes a single key lookup taking microseconds instead of a complex database query taking seconds.
The tradeoff
Redis is not the source of truth -- it's a cache. The real data lives in a relational database. If Redis goes down, the data isn't lost -- just slow until the cache rebuilds.
G LinkedIn Neo4j / custom graph ▾
"People you may know", connection degrees
Why graph
LinkedIn's entire value proposition is the professional network -- who knows who, through how many degrees. "You and this person share 12 connections" requires traversing a web of relationships. In a relational database this would require many expensive joins. A graph database is purpose-built to traverse exactly this kind of connected data.
The tradeoff
Graph databases are specialized. LinkedIn still uses relational databases for profiles, messages, and jobs -- the graph layer is specifically for relationship traversal and recommendations.
T Cloudflare InfluxDB / Prometheus ▾
Network traffic metrics, request rates, latency
Why time-series
Cloudflare processes trillions of requests and needs to track metrics -- requests per second, error rates, latency -- continuously across thousands of servers. This data is always in time order and always being queried by time range ("show me error rates for the last hour"). A time-series database is optimized exactly for this write-heavy, time-ordered workload.
The tradeoff
Time-series databases typically auto-expire old data (you don't need millisecond metrics from 3 years ago). They're append-only -- you don't update or delete individual records.
C Spotify BigQuery / Cassandra ▾
Listening history analytics, recommendation engine
Why columnar
Spotify needs to analyze billions of listening events to power Discover Weekly and Wrapped. Queries like "find all users who listened to jazz on Friday evenings in the last 6 months" scan one column across billions of rows. A columnar store does this orders of magnitude faster than a row-oriented database because it only reads the columns it needs.
The tradeoff
Columnar databases are read-optimized, not write-optimized. Spotify uses separate operational databases for things that need fast individual writes (play events, playlists) and the columnar store for analytics.
Brand name directory
R Relational / SQL structured, consistent ▾
PostgreSQL, MySQL, SQLite, MariaDB, Oracle, SQL Server
PostgreSQL
Open source, full-featured, widely used in production. The go-to choice for most new projects. Often called "Postgres".
MySQL
Open source, extremely common, powers a huge portion of the web. Used by Facebook, Twitter, YouTube historically.
SQLite
Lightweight, serverless -- the entire database is a single file. Used in mobile apps, browsers, and local development. Not for multi-user production.
MariaDB
A fork of MySQL created when Oracle acquired MySQL. Drop-in compatible with MySQL.
Oracle / SQL Server
Enterprise commercial databases. Common in large corporations and legacy systems.
D Document stores flexible, JSON-like ▾
MongoDB, CouchDB, Firestore, DynamoDB (also key-value)
MongoDB
The most popular document database. Stores BSON (binary JSON). Very common in JavaScript / Node.js stacks.
Firestore
Google's cloud document database. Very popular for mobile and web apps due to real-time sync capabilities.
CouchDB
Open source, strong sync capabilities. Less common but used in offline-first applications.
DynamoDB
Amazon's managed database. Technically a key-value and document store hybrid. Extremely scalable.
K Key-value stores fast, simple lookups ▾
Redis, Memcached, DynamoDB, etcd
Redis
By far the most popular. In-memory, extremely fast. Supports more than just key-value -- also lists, sets, sorted sets. Used for caching, queues, pub/sub, and rate limiting.
Memcached
Simpler and older than Redis. Pure caching, nothing else. Still used at scale (Facebook uses it heavily) but Redis has largely superseded it for new projects.
etcd
Distributed key-value store used for configuration and service discovery. The backbone of Kubernetes.
G Graph databases relationships, networks ▾
Neo4j, Amazon Neptune, ArangoDB, TigerGraph
Neo4j
The most widely used graph database. Uses its own query language called Cypher. Strong community and tooling.
Amazon Neptune
AWS's managed graph database. Supports both property graphs and RDF (knowledge graphs).
ArangoDB
Multi-model database -- handles documents, key-value, and graphs in one system.
T Time-series databases metrics, events, monitoring ▾
InfluxDB, Prometheus, TimescaleDB, Graphite
InfluxDB
Purpose-built time-series database. Very common for infrastructure monitoring and IoT data.
Prometheus
Open source monitoring and alerting. Stores metrics as time-series. The standard in cloud-native / Kubernetes environments.
TimescaleDB
Built on top of PostgreSQL -- adds time-series capabilities to a relational database. Good if you want SQL familiarity with time-series performance.
C Columnar / analytics warehousing, big data ▾
BigQuery, Redshift, Snowflake, Cassandra, ClickHouse
BigQuery
Google's fully managed data warehouse. Serverless -- you just run queries and pay per data scanned. Very popular for analytics.
Redshift
Amazon's data warehouse. Columnar storage, integrates tightly with the AWS ecosystem.
Snowflake
Cloud-native data warehouse that separates storage and compute. Very popular in enterprise analytics.
Cassandra
Apache's distributed database. Handles massive write volumes across many servers. Used by Netflix, Apple, and Instagram for high-scale operational data.
ClickHouse
Open source columnar database known for extremely fast analytical queries. Growing quickly in popularity.
