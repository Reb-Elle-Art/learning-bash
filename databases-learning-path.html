The goal
To be a smart decision-maker and evaluator of database choices -- not a database engineer. To understand the landscape well enough to scope out the right database for a project, think through tradeoffs, and intelligently evaluate recommendations from developers or agents.
The concentric circle model

Three rings of knowledge, built outward. Click each to expand.

1
Core -- SQL as a mental model
The vocabulary everything else is built on or compared to
~10 hours
▾
What this is
SQL is the baseline language of databases. Even if you never write production SQL, understanding how it thinks -- tables, rows, relationships, joins -- gives you the vocabulary to understand every other database type by comparison. NoSQL is defined by what it isn't. Vector databases are explained relative to what SQL can't do well. It all starts here.
What you're building
Conceptual fluency. Enough SQL to read and reason about a query, not to write production code. The ability to look at a data structure and understand how it would be represented relationally.
What you're not doing
Stored procedures. Query optimization. Database administration. Indexing strategies. That's database engineering territory -- not your goal.
Marker for completion
You can read a SQL query and explain in plain language what it's asking. You can describe the difference between a primary key and a foreign key without looking it up.
2
Middle ring -- database categories
One focused deep-dive per type, in order of conceptual dependency
~15 hours
▾
The approach
For each category: understand the core concept, understand when you'd choose it, understand what you'd be giving up, do one sandbox session to make it real. You don't need to master any of these -- you need to place them on a map and understand the tradeoffs.
The order
Relational first (builds on the core). Then Vector -- moved up because it is increasingly central to modern systems and best understood early. Then Document, Key-Value, and Graph.
Marker for completion
Given a project description, you can name the likely database category and explain why. You can explain what a vector database is doing that a relational database can't.
3
Outer ring -- decision making
Evaluating recommendations, asking the right questions, thinking through tradeoffs
ongoing
▾
What this is
Not a phase you complete -- a way of thinking you develop as the inner rings solidify. The ability to receive a recommendation and interrogate it. To ask "why this and not that" and understand the answer. To recognize when a recommendation is well-reasoned vs when it's just the default.
Your project as a case study
Apply this thinking to any real system you interact with. What database is it using? Why? What would you change? The best practice is a real project you can interrogate throughout the learning process.
Marker for completion
There isn't one. This is the goal, not the endpoint.

A note on time
This isn't a sprint. A couple of hours a week, no deadline, no stopping until you understand it. The concentric circle model means you're always building -- finishing the core makes the middle ring easier, and the middle ring makes evaluation instinctive. There's no wrong place to pause.

Core -- SQL as a mental model
S
SQL concepts & vocabulary
~5-10 hrs
▾
What to internalize
Tables, rows, columns. Primary and foreign keys. SELECT, WHERE, ORDER BY. JOINs -- what they are and why they exist. GROUP BY and aggregates. Schema as a concept. ACID properties and why transactions exist.
How
Read first, then do. Start with the Databases reference page here to ground the vocabulary. Then go interactive -- SQL Murder Mystery is the recommended first hands-on experience. Self-directed, low pressure, builds real intuition.
Deep dive
Work through at least one gamified resource end to end. The goal is to get SQL syntax into your fingers -- not to memorize it, but to feel comfortable reading it. Pay particular attention to JOINs: understanding why they exist (to avoid duplicating data across tables) is the conceptual key to the whole relational model.
What done looks like
You can read a SQL query and explain in plain language what it's asking. You understand why JOINs exist. You can describe primary vs foreign key without looking it up.

Middle ring -- database categories in order
R
1. Relational -- PostgreSQL
~3 hrs
▾
Why first
Everything in the middle ring is understood relative to relational. Document stores are "relational but flexible." Vector databases are "relational but for meaning not structure." You need the baseline.
What to internalize
What PostgreSQL is and why it is the default choice for most new projects. How schemas enforce structure and why that matters. What a JOIN does at a data level -- not just the syntax, but the concept of linking normalized data. When relational is the right choice and when it starts to strain.
Deep dive
Read the Applications tab on the Databases page -- specifically the Instagram and Airbnb examples side by side. They illustrate exactly when relational is the right call (Instagram -- consistent structure, clear relationships) vs when it starts to strain (Airbnb -- every listing is different). Then look at the Brand Name Directory to understand where PostgreSQL sits relative to MySQL, SQLite, and the enterprise options.
Sandbox
If you want hands-on: SQLBolt has exercises that use a real relational schema. Run through the JOIN exercises specifically -- they are the conceptual core of this phase.
What done looks like
Given a project with structured, consistent data and clear relationships, you would recommend relational and explain why. You can explain what a schema constraint is and why it matters. You understand why Airbnb might not use relational for listings.

Applications tab -- Databases page SQLBolt -- JOIN exercises PostgreSQL docs intro
V
2. Vector databases
~3 hrs
▾
Why second
Vector databases are increasingly central to modern AI-adjacent systems. Understanding them early means you can evaluate architectures that involve semantic search or cross-source querying from the start -- which comes up constantly in AI-era system design.
What to internalize
What an embedding is -- a mathematical representation of meaning, not just data. What similarity search means vs keyword search: the difference between "find rows where tag = AI" and "find everything conceptually related to AI." Why this category didn't exist before LLMs. The difference between storing data and storing meaning. Key names: Pinecone, Weaviate, Qdrant, Chroma. Also pgvector -- vector search layered inside PostgreSQL, which matters because it means you don't always need a separate vector database.
Deep dive
Read the Coursera explainer first -- it covers embeddings clearly without assuming ML background. Then try one of the sandboxes. Weaviate has a well-designed onboarding that walks you through storing and querying by similarity without needing to write any embedding code yourself. The goal is to feel what "search by meaning" actually does differently from a SQL WHERE clause.
Key question to sit with
If someone says "we're using a vector database for search" -- what are they actually doing? What would break if they used a relational database with a LIKE query instead? Being able to answer that concretely is the marker for this phase.
What done looks like
You can explain what an embedding is to someone who hasn't heard the term. You understand why a knowledge base with cross-source querying needs a vector layer and not just tags or keyword search.
Resources
Weaviate sandbox Qdrant sandbox Coursera -- Vector DB explained
D
3. Document -- MongoDB
~3 hrs
▾
What to internalize
Collections vs tables. Documents vs rows. Why flexible schema matters -- and when it becomes a problem. The key tension: flexibility vs consistency. Embedding vs referencing -- when do you nest data inside a document vs point to another document? Why MongoDB became the most popular NoSQL database and what it sacrifices to get there.
A good mental model
Think about content that varies by type -- a PDF has different metadata than a video, which has different metadata than a URL. A relational schema would require many nullable columns or complex joins to handle this. A document store lets each record carry exactly the fields it needs, nothing more. This is the core tradeoff: flexibility at the cost of enforced consistency.
Deep dive
Read the Airbnb example in the Applications tab on the Databases page -- it's the clearest real-world illustration of why you'd choose document over relational. Then try MongoDB Atlas free tier: create a collection, insert a few documents with different shapes, and query across them. The moment you insert two documents with different fields into the same collection and it just works -- that's the "aha" for this phase.
Watch for
The flexible schema that feels like a feature early on can become a liability at scale -- when no two documents look the same and you need to query across all of them. Understanding when document stores cause problems is as important as understanding when they solve them.
What done looks like
You can explain why a content management system or product catalog would use a document store over relational. You understand the tradeoff between flexibility and consistency. You can describe what "embedding vs referencing" means in document database design.
Resources
MongoDB Atlas free tier Applications tab -- Databases page MongoDB docs intro
K
4. Key-value -- Redis
~2 hrs
▾
What to internalize
The dictionary mental model -- every piece of data is stored under a unique key and retrieved by that key. Why in-memory is fast (no disk reads). TTLs and expiration -- why you'd want data to automatically disappear after a set time. Why Redis is almost always used alongside another database, not instead of one. Common use cases: caching (store the result of an expensive query so you don't run it again), sessions, rate limiting, queues.
Deep dive
The Redis online editor lets you run commands in the browser without installing anything. Try SET, GET, EXPIRE, and TTL. Then look at the Twitter/X example in the Applications tab -- it's the clearest illustration of what caching actually solves and why you'd reach for Redis specifically. The key insight: Redis is not a replacement for your main database. It's a fast layer in front of it.
Key question to sit with
If a developer says "we cache that in Redis" -- what does that mean concretely? Where does the real data live? What happens if Redis goes down? Being able to answer those three questions is the marker for this phase.
What done looks like
If someone recommends adding Redis to a project, you understand what problem it's solving and what it isn't responsible for. You can explain the caching pattern -- source of truth in a relational database, hot data in Redis -- without looking it up.
Resources
Redis online editor Applications tab -- Databases page Redis docs
G
5. Graph -- Neo4j
~3 hrs
▾
What to internalize
Nodes (things) and edges (relationships between things) as the primary data model. Traversal vs JOIN -- in a relational database, connecting two things requires a JOIN across tables; in a graph database, relationships are first-class citizens stored directly as edges. This is a fundamentally different operation at a structural level. When "how things are connected" and "through how many steps" matters more than "what things contain." Cypher query language at a surface level -- enough to read a query, not write production code.
Deep dive
Read the LinkedIn example in the Applications tab -- "people you may know" is the canonical graph problem and it makes the case clearly. Then try the Neo4j sandbox: it loads a pre-built movie database and walks you through Cypher queries. The goal is to run a traversal query -- "find all actors who worked with someone who worked with Tom Hanks" -- and feel the difference from a SQL JOIN. That query would require multiple JOINs and subqueries in SQL. In Cypher it's one line.
Watch for
Graph databases are specialized. They are not a replacement for relational -- most systems that use Neo4j also use PostgreSQL for everything that isn't relationship traversal. The question is never "should we use graph instead of relational" -- it's "do we have a relationship traversal problem that justifies adding a graph layer?"
What done looks like
You can describe a use case where graph is clearly the right choice and explain in concrete terms why relational would struggle with the same problem. You can read a Cypher query and understand roughly what it's asking.

Outer ring -- decision making

Evaluating recommendations
ongoing
▾
What this is
The ability to receive a database recommendation and ask the right questions. To understand whether it's well-reasoned or just the default. To think through tradeoffs without needing to implement them.
How you build this
It emerges from the inner rings. As each category becomes familiar, evaluation becomes instinctive. The Evaluating tab gives you the specific questions to ask.
Your project as practice
At every stage, apply the thinking to a real system you interact with. What is it storing? How is it querying? What database is it likely using? Is that the right choice? Why or why not?

Questions to ask when evaluating a database recommendation. Click to expand the reasoning.

Questions about the data
What does the data actually look like -- and does it have a consistent structure?
▾
If every record looks the same (same fields, same types), relational is probably right. If records vary significantly -- different fields per item, nested structures -- a document store may be better. This is the first filter.
Are the relationships between data points as important as the data itself?
▾
If you're constantly asking "what is connected to what, and through how many steps," that's a graph problem. If your relationships are simple (this order belongs to this user), relational handles it fine. The complexity of relationship traversal is the key question.
Is the querying keyword-based or meaning-based?
▾
"Find all records tagged 'machine learning'" is keyword-based -- any database handles this. "Find everything conceptually related to machine learning" is meaning-based -- that requires a vector layer. If cross-source querying needs to surface conceptually related content, vector is involved.
How does the data change over time -- and how often?
▾
Relational databases handle frequent updates to individual records well. Time-series databases are for append-only, time-stamped data queried by range. Columnar databases are optimized for reads across many rows, not frequent writes. The write pattern shapes the choice.
Questions about the recommendation
Why this database specifically -- not just this category?
▾
"We need a document database" is a category choice. "We're using MongoDB" is a product choice. They're different decisions. Ask why MongoDB over Firestore, or PostgreSQL over MySQL. The answer reveals whether the recommendation is well-reasoned or just habitual.
What are we giving up with this choice?
▾
Every database choice is a tradeoff. Document stores sacrifice consistency for flexibility. Key-value stores sacrifice queryability for speed. A good recommendation comes with an honest account of what you're trading. If someone can't articulate the tradeoff, the recommendation isn't well-reasoned.
Is this the right database for now, or for where we're going?
▾
SQLite is perfect for a local prototype. It doesn't scale to a million users. PostgreSQL scales much further. Ask whether the recommendation accounts for scale -- and whether that scale is actually realistic for this project.
Is this a single-database recommendation or a layered one?
▾
Most real systems use more than one database type. PostgreSQL for structured data, Redis for caching, a vector store for semantic search. A recommendation that tries to do everything with one database may be oversimplified. Ask whether the architecture accounts for different access patterns having different storage needs.
Is this the default choice, or the right choice?
▾
Developers and agents have defaults -- technologies they know, ecosystems they're comfortable in. Ask what alternatives were considered and why they were ruled out. The answer tells you a lot about the depth of the reasoning.
A worked example -- knowledge base systems
The project
A knowledge base that ingests content from multiple source types (documents, URLs, video transcripts), categorizes it, creates stub entries, and allows querying across sources by concept.
Likely database layers
Document or relational -- for the stub entries. If metadata varies by source type, document is more natural. If it's consistent, relational works fine.

Vector -- for querying by meaning across sources. "Find everything related to X" requires embedding the content and doing similarity search. Almost certainly in the stack.

Key-value (maybe) -- for caching frequent queries or session state.
Questions to ask
What database is storing the entries? How is cross-source querying implemented -- keyword or semantic? Is there a vector store involved? If so, which one and why?
